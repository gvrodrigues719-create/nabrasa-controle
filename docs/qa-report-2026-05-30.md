## P0 — Crítico

### BUG-01: `LOCAL_KEY` sem `userId` — contaminação cruzada em dispositivo compartilhado
**Arquivo:** `src/app/dashboard/count/[routineId]/[groupId]/page.tsx:32`  
**Código atual:**
```ts
const LOCAL_KEY = `count_${routineId}_${groupId}`
```
**Problema:**  
A chave de localStorage não inclui o `userId`. Em dispositivos compartilhados (tablet de operação), se o Usuário A inicia uma contagem e não finaliza, o Usuário B que abre o mesmo grupo herda os dados do Usuário A. O código em `initSession()` carrega o localStorage ANTES de verificar o DB:

```ts
const stored = localStorage.getItem(LOCAL_KEY)
const localDict: Record<string, string> = stored ? JSON.parse(stored) : {}
// ...
const newCounts = { ...localDict }  // contamina antes de checar DB
```

**Cenário real:** Operador A conta 50 itens na Câmara Fria e sai sem concluir. Operador B abre a mesma Câmara Fria — vê os números de A pré-preenchidos e os submete como seus, sem saber.

**Correção:**
```ts
const { data: { user } } = await supabase.auth.getUser()
const LOCAL_KEY = `count_${user.id}_${routineId}_${groupId}`
```

## P1 — Alto

### BUG-02: Janela de perda de dados na persistência delete→insert não atômica
**Arquivo:** `src/app/dashboard/count/[routineId]/[groupId]/page.tsx:216-262` e `:311-349`

**Problema:**  
`persistCounts()` e `executeCompleteGroup()` ambos executam:
1. `DELETE FROM count_session_items WHERE session_id = sid`  
2. `INSERT INTO count_session_items ...`

Entre o DELETE e o INSERT existe uma janela onde o DB não tem dados. Se a conexão cair, o browser fechar, ou o Supabase retornar erro no INSERT após o DELETE ter sucedido, **todos os dados da sessão somem do banco**. O localStorage serve de backup, mas só se o MESMO usuário/dispositivo voltar.

**Cenário Camboinhas:** Se a rede instável durante a conclusão causou o DELETE a passar mas o INSERT a falhar, a sessão `in_progress` persiste no banco sem itens. Na próxima vez que o operador abre o grupo, `initSession()` encontra a sessão vazia, carrega o localStorage (se ainda estiver lá), e o operador pode refazer.

**Mitigação existente:** A auto-recuperação de localStorage em `initSession()` (adicionada em b0f3727) cobre parcialmente esse cenário, mas apenas se o operador retornar ao mesmo grupo no mesmo dispositivo.

**Correção ideal:** Usar `upsert` com a constraint `UNIQUE(session_id, item_id)` ou envolver em transação via RPC. Alternativa mais simples: salvar counts em uma coluna JSONB na própria `count_sessions` em vez de linhas separadas.

### BUG-03: Filtro de sessões por data cria estado inconsistente entre Groups e Count pages
**Arquivos:**  
- `src/app/dashboard/routines/[id]/page.tsx:57` — filtra por hoje  
- `src/app/dashboard/count/[routineId]/[groupId]/page.tsx:59-67` — filtra por `neq('status', 'completed')`

**Problema:**  
A página de grupos (`routines/[id]`) só carrega sessões de hoje:
```ts
.gte('started_at', `${today}T00:00:00Z`)
```

Mas a página de contagem encontra **qualquer** sessão não-completada:
```ts
.neq('status', 'completed')
```

**Cenário:** A Camboinhas tem uma sessão `in_progress` de ontem (ex.: operador esqueceu de finalizar). A página de grupos mostra o grupo como "Disponível" (verde — sem sessão hoje). Operador clica, entra no grupo, a página de contagem detecta a sessão de ontem e a reutiliza silenciosamente, mostrando os dados de ontem. O operador não percebe que está contando sobre dados velhos.

**Correção:** Alinhar os filtros: ou ambos usam `neq('status', 'completed')` (mostrando sessões antigas), ou a página de contagem também filtra por hoje e cria nova sessão caso só exista sessão antiga.

### BUG-04: Rotas de admin acessíveis diretamente sem verificação de role na UI
**Arquivos:** `src/app/dashboard/admin/items/page.tsx`, `src/app/dashboard/admin/groups/page.tsx`, `src/app/dashboard/admin/routines/page.tsx`

**Problema:**  
O `dashboard/layout.tsx` só verifica se há sessão autenticada. Não verifica `role`. As páginas admin não têm proteção de role no componente — qualquer usuário autenticado que digitar `/dashboard/admin/items` na URL tem acesso à interface CRUD.

O banco (RLS) bloqueia operações de INSERT/UPDATE/DELETE para operadores, mas:
1. A UI de edição/exclusão fica visível e clicável
2. O operador pode tentar ações que falham silenciosamente ou com erro confuso

**Cenário:** Operador de Camboinhas acessa `dashboard/admin/items` manualmente e tenta excluir um item — vê o botão de lixeira, clica, o modal aparece, confirma, e recebe um erro vago de RLS.

**Correção:** Adicionar verificação de role no `useEffect` de cada página admin, ou criar um `AdminLayout` com redirect para não-admins.

## P2 — Médio

### BUG-05: Double-click no botão "Concluir Grupo" pode disparar `handleCompleteGroup` duas vezes
**Arquivo:** `src/app/dashboard/count/[routineId]/[groupId]/page.tsx:279-297`

**Problema:**  
O botão de conclusão não tem `disabled` durante o processamento nem debounce:
```tsx
<button onClick={handleCompleteGroup} ...>
```

`handleCompleteGroup` chama `setIsConfirming(true)` para abrir o modal. Como `setState` é assíncrono, um double-click rápido pode chamar `handleCompleteGroup` duas vezes antes do re-render com `isConfirming=true`. O resultado prático é o modal abrindo duas instâncias (ou a segunda chamada sendo no-op porque o estado de `syncStatus` foi checado).

Na prática, o `ConfirmModal` usa `if (!isOpen) return null` — portanto duas chamadas resultam em dois modais sobrepostos se o estado atualizar entre elas, ou num modal com duplo handler `onConfirm` que chama `executeCompleteGroup` duas vezes.

**Correção:**
```tsx
<button onClick={handleCompleteGroup} disabled={isConfirming || syncStatus === 'saving'} ...>
```

### BUG-06: `LOCAL_KEY` no `handleChange` não reflete mudança de sessionId pós-init
**Arquivo:** `src/app/dashboard/count/[routineId]/[groupId]/page.tsx:264-269`

**Problema:**  
`LOCAL_KEY` é definida na linha 32, antes do `initSession()`. Depois que `initSession()` resolve e o `sessionId` é definido (via `setSessionId`), o `LOCAL_KEY` não muda — está capturado no closure da função de componente com os valores do render inicial.

Isso não é um bug funcional pois `LOCAL_KEY` só depende de `routineId` e `groupId` (imutáveis), mas documenta a intenção errônea de eventualmente incluir `userId`, que exigiria que `LOCAL_KEY` fosse calculado DENTRO do `initSession()` para ter acesso ao `user.id`.

### BUG-09: `execution_id` armazenado em `sessionStorage` — não persiste entre abas
**Arquivo:** `src/app/dashboard/routines/[id]/page.tsx:87-89`
```ts
sessionStorage.setItem(`exec_${routineId}`, executionId)
```
`sessionStorage` é específico por tab e não persiste ao fechar o browser. Se o operador abrir o grupo de contagem em uma nova aba (ou reabrir o browser), `execution_id` será null na nova sessão de contagem (`count_sessions.execution_id = null`), desassociando a sessão do ciclo de execução no histórico.
